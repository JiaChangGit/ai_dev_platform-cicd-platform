# Governance：審查政策（Review）

> 審查「怎麼做」見 `workflow/review.md`；本文件定義**強制規則**。

## 核准門檻（建議預設值，依團隊規模調整）

| 變更類型 | 最少核准人數 | 備註 |
|---|---|---|
| 一般 feature / bugfix | 1 | 小型團隊或個人專案可為自我檢查 + AI 交叉審查 |
| 涉及安全性、權限、加密 | 2 | 至少一位需具備該領域背景 |
| 架構層級變更（有 ADR） | 1（含 ADR 制定者以外的人） | ADR 本身也需經審查 |
| Hotfix | 事後補審 | 合併前至少 1 人快速過目 |

## 規則

- 作者不得核准自己的 PR
- CI 必須全綠才能合併，除非有明確記錄的例外理由
- 審查意見中標記為 blocking 的項目，必須全部解決或由審查者明確撤回才能合併
- 使用 CODEOWNERS（或等效機制）指定特定路徑的必要審查人
- AI 產出與人工撰寫的程式碼適用相同審查標準。AI 產出還須檢查不存在的 API、套件與過時資訊

## AI 擔任 reviewer 時的最低獨立性要求

多 AI 角色分工（`registry/providers.yaml`）不是形式，是這條規則要生效的前提：**同一個 context、同一次對話裡「順便」自己審自己寫的東西，不算獨立審查**，即使技術上是兩個不同的 tool call。

- Reviewer 角色至少要滿足以下其中一項，才算獨立：
  - 用不同 provider/模型執行（例如 implementer 用一個廠商的模型，reviewer 換另一個）
  - 或用全新、不含實作過程對話歷史的 context 執行，且只看 diff 與需求描述、不看實作時的討論
- 任務只有單一執行者且沒有第二個獨立角色時，須告知使用者本次未完成獨立審查，由使用者決定是否補充人工審查；AI 不得自行核准
- 這條規則對 `governance/security.md` 列出的高風險變更沒有例外——沒有獨立 reviewer 時，那類變更不得標記為「已審查」

這是收尾三層驗證的第二層，另外兩層（typecheck/test/build、外部引用自我核對）見 `governance/agent-discipline.md` 第 2 節。

## 升級機制

審查意見出現分歧、或審查者與作者對設計方向有根本歧異時，先在 PR 討論串釐清；仍無共識時，升級給對應模組負責人或架構負責人裁定，並將結論記錄（必要時補一份 ADR）。
