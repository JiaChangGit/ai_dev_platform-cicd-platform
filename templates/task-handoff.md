# Task Handoff 模板

用於 `registry/workflow.yaml` 中 `handoff_required: true` 的任務，在角色交接（例如 planner → implementer、implementer → verifier）時產出。**寫成實體檔案**，不要只留在對話紀錄裡——CLI 呼叫通常是無狀態的，下一個角色開新的 context 時看不到上一輪的對話，只看得到檔案。

建議存放位置：產品儲存庫的 `.ai/handoffs/<task-id>/<seq>-<from-role>-to-<to-role>.md`（任務結束後可歸檔或刪除，不需要長期保留在主要文件樹中）。

```markdown
# Handoff: <task-id> — <from-role> → <to-role>

## 任務
（一句話：這個任務原本要做什麼；連結對應 issue）

## 我（<from-role>）完成了什麼
-

## 關鍵決策與理由
（做了哪些選擇、為什麼這樣選、有沒有考慮過其他做法但放棄了——下一個角色不該重新猜一次）
-

## 明確假設（尚未經使用者確認）
（任何「我先假設是這樣做下去」的地方，明確列出來，讓下一個角色知道這不是已確認的事實）
-

## 已知限制 / 未解問題
-

## 交給 <to-role> 的具體任務
（不重複原始需求；只列已完成項目之後的具體任務。）
-

## 相關檔案 / 變更範圍
（改了哪些檔案、新增了哪些檔案，讓下一個角色知道去哪裡看）
-

## 驗證方式
（<to-role> 完成後，怎麼確認交接的東西是對的——對應 registry/workflow.yaml 該任務的 deliverables）
```

## 使用原則

- 只寫「下一個角色不知道、但需要知道」的內容，不要把整個對話紀錄複製貼上
- 「關鍵決策與理由」與「明確假設」兩節最容易被省略，但也是最容易讓下一個角色做錯方向的地方，不要跳過
- 若交接後發現上一個角色的假設是錯的，不要默默改掉重做；回頭更新這份交接檔案並標註為什麼原假設不成立，讓決策過程可追溯
