# Workflow：Code Review 操作流程

> 本文件說明審查時「實際怎麼做」。誰必須審查、需要幾人核准等**強制規則**見 `governance/review.md`。

## 身為審查者

1. **先看意圖**：讀 PR 描述與連結的 issue，理解「這個改動想解決什麼」，再看 diff
2. **檢查清單**（依序）：
   - 正確性：邏輯是否符合描述的需求與驗收標準
   - 測試：是否有對應測試，以及斷言是否驗證實際行為，而非只執行流程
   - 邊界情況：錯誤處理、空值、併發、資源釋放
   - 風格與一致性：是否符合專案既有慣例（不是審查者個人偏好）
   - 安全性：是否可能引入 `governance/security.md` 列出的風險項目
   - 文件：對外行為改變時是否同步更新文件
   - 範圍：改動是否聚焦，有沒有夾帶不相關的變更
3. **給意見的方式**：
   - 區分「必須改（blocking）」與「建議（nit / suggestion）」，明確標註
   - 指出問題時，盡量附具體修改建議或範例，而不是只說「這裡怪怪的」
   - 對 AI 產出的程式碼，額外檢查是否有「看起來合理但實際上是幻覺」的 API 呼叫、套件名稱、設定參數

## 身為 PR 作者

1. 自己先跑過一次第 2 點的檢查清單再送審
2. 回覆審查意見時，逐項回應（已修正 / 有不同看法並說明原因 / 需要進一步討論）
3. 對每個 blocking 意見，確認修正後再請求重新審查

## 特殊情況

- **大型 PR**：優先考慮拆成多個小 PR；若無法拆，審查者可要求作者先提供一份變更摘要導覽
- **緊急修復（hotfix）**：可縮短審查時間，但不可跳過審查本身，事後補一次完整審查
