AI Dev Platform
架構、導入與發行邊界

這套平台放在多個產品旁邊共用。它不保存產品程式碼，也不代替 CI/CD；實際提供規則、工作流程、模板、離線第三方 skill、初始化工具與發行驗證程式。

內容依據：本頁以 scripts/*.py、tests/、distribution/*.json、CI workflow 與產品入口模板為準。若敘述與程式行為不同，必須以測試釐清並同步修正。
1 個共用唯讀平台產品固定讀取相鄰 ai-dev-platform/ 的目前版本。
每項產品 2 個 Git repo開發 repo 保存原始碼；release repo 只保存發行中繼資料。
4 種 CI 入口GitHub Actions、GitLab CI、Jenkins、internal CI。

1. 專案目的

平台把跨產品共用規則，與產品自己的程式碼、CI、領域規範及發行紀錄分開。Android App、SSD PCIe 韌體或其他領域可共用任務分類、審查與發行證據格式，但仍使用各自核准的工具鏈。

程式實作能力實際行為未提供的能力
平台發行包（platform package）依 distribution/manifest.json 建立單一頂層 ZIP，記錄逐檔 SHA-256、大小與權限。不把維護 repo 的 .git 放進下載包。
原子安裝（atomic install）先驗證 ZIP 與 sidecar SHA-256，在暫存目錄解壓並執行自我檢查，成功後才替換舊平台。目標含 .git 時拒絕替換。
產品初始化（bootstrap）建立 <product>-cicd-platform 與 <product>-release，預設各自執行 git init。不覆寫既有同名目錄。
CI 轉接產生四種 CI 的 build／test／lint 骨架與 release evidence 轉接模板。不提供產品工具鏈、runner 帳號、成品空間或憑證。
發行驗證檢查版號、來源 commit、必要 checks、hash、簽章、SBOM、SLSA、獨立核准與 tag。不把實際成品、私鑰、SBOM 或簽章存進 release repo。
工具入口的真實範圍：初始化程式產生 AGENTS.md、CLAUDE.md、opencode.json，對應 Codex、Claude Code、opencode。其他工具若不讀這些格式，必須另做轉接。

2. 架構與物件關係

工作區採平行目錄，不用 Git submodule 或 subtree 把平台複製到產品 repo。產品 metadata 固定為 platform: ../ai-dev-platform 與 platformVersionPolicy: always-current。

Work/ai-dev-platform/已驗證 ZIP 的安裝結果；沒有 .git，預設檔案唯讀。
Work/product-cicd-platform/產品原始碼、測試、CI/CD、架構與領域規範；獨立 Git repo。
Work/product-release/同產品專屬的發行中繼資料；另一個獨立 Git repo。
ai_dev_platform-cicd-platform/ 只供平台維護、第三方同步與產生下一版 ZIP。一般產品工作區只需要已安裝的 ai-dev-platform/。

4. 建立與導入步驟

A. 建立唯讀平台

1

驗證維護來源

開發中可用 --allow-dirty 診斷；正式包必須對應乾淨 commit。

2

建立與驗證 ZIP

封裝器記錄逐檔 hash、大小、mode，驗證後才發布正式檔名。

3

安裝到 Work

先在暫存目錄驗證與自我檢查，再原子替換並設為唯讀。

# 平台維護 repo
bash scripts/check.sh
python3 -B -m unittest discover -s tests -v
python3 -B scripts/audit_skills.py
python3 -B scripts/pre_push_audit.py
python3 -B scripts/package_release.py --source-ref "$(git rev-parse HEAD)"
python3 -B scripts/verify_package.py dist/ai-dev-platform-1.3.0.zip

# <Work> 換成共同父目錄；先預覽再安裝
python3 -B scripts/install_platform.py dist/ai-dev-platform-1.3.0.zip \
  --work-root <Work> --dry-run
	python3 -B scripts/install_platform.py dist/ai-dev-platform-1.3.0.zip \
	  --work-root <Work>
CI 模式：GitHub Actions、GitLab CI 或其他 runner 不建立 commit 時，使用 python3 -B scripts/pre_push_audit.py --ci。這只略過 runner 的 user.name／user.email，敏感資料、remote、忽略規則與建置成品仍是阻擋條件。
不要在 ai-dev-platform/ 執行 git init。安裝器發現目標含 .git 會停止，避免把維護 repo 當成可替換的下載包。

C. 建立通用領域產品

generic 沒有預設工具鏈；下列產品資訊與命令全部必填。平台會驗證為非空單行字串與安全相對 artifact path，但不會猜測命令是否符合未知框架。

python3 -B scripts/init_product.py \
  --name sample-service --display-name "Sample Service" \
  --domain generic --ci jenkins \
  --product-type "Web Service" --target-platform "Linux container" \
  --language-framework "<實際技術>" \
  --build-command "<build command>" --test-command "<test command>" \
  --lint-command "<lint command>" --package-command "<package command>" \
  --artifact-path "dist/<artifact-name>"

D. 初始化後必須補齊

項目狀態設定內容
registry/providers.yaml必要目前 model ID 是 REPLACE_WITH_ACTUAL_MODEL_ID。換成實際可用設定，或移除不用的範例。
docs/domain-standards.md必要補產品核准的一手規格、SDK、工具鏈版本與限制。
CI runner／成品平台必要設定 runner、不可變成品 URI、簽章金鑰管理、SBOM 與 SLSA。
CODEOWNERS／獨立核准必要加入真實協作者；PR 作者不能自我核准，publisher 不能等於 release approver。
外部框架選用OpenSpec、grill-with-docs、superpowers 不是核心依賴，需要時再啟用。

5. 使用案例

Android App

  • Build：gradle --no-daemon :app:assembleDebug
  • Test：gradle --no-daemon :app:testDebugUnitTest
  • Lint：gradle --no-daemon :app:lintDebug
  • Package：gradle --no-daemon :app:assembleRelease

最小範例含 AndroidManifest、入口 Activity 與 JUnit 測試。GitHub workflow 另設定 JDK 17 與 Gradle 9.4.1。

SSD PCIe 韌體

  • Build：make all
  • Test：make test
  • Lint：make lint
  • Package：make package

最小範例使用 C11 與 Make；測試會實際建立非空 ELF。它只驗證平台能承載韌體流程，不代表真實控制器、NVMe 或 PCIe 行為。

其他產品

用 generic 建立 web service、kernel module、CLI 或其他專案時，必須明確提供 build／test／lint／package 命令與安全相對 artifact path。

平台不替未知領域選語言、套件管理器、編譯器或安全規範。

Release repo 採允許清單（allowlist）

verify_release_layout.py 只接受：

  • 必要管理檔：README.md、AGENTS.md、CLAUDE.md、opencode.json、.gitignore、CODEOWNERS 與允許的 CI 設定。
  • release-evidence/<version>.json。
  • release-notes/<version>.md。
  • Git tag v<version>。

原始碼、external/、APK、AAB、ELF、韌體映像、ZIP、SBOM 實體檔與簽章實體檔都不能進入 release repo。

7. 移除 DEV 專案的開發紀錄

先分清楚移除位置。平台維護 repo 與產品開發 repo 需要 Git commit 來驗證 sourceRef、版本與來源關係，不能為了讓下載包乾淨就刪除它們的 .git。正確做法是由封裝器建立不含 Git 的 ZIP，再安裝成唯讀平台。
項目處理程式上的理由
維護 repo 的 .git/保留正式 package 要對應不可變 commit；readiness 也會核對來源 commit／ref。
產品開發 repo 的 .git/保留產品原始碼、審查與 CI 的來源。
發行 repo 的 .git/獨立重建只連接同名的空白遠端；若遠端已有歷史就重新 clone，不得 force push。
下載 ZIP 內的 .git/必須排除distribution manifest 排除，package verifier 也拒絕 Git 內部路徑。
.ai/handoffs/不進 Git可能含任務上下文、問題細節、檔名或內部資訊。
dist/、build/、__pycache__/、.gradle/不進 Git可重建的本機輸出，由 .gitignore 與 package exclude 處理。
local.properties、IDE／個人工具設定不進 Git可能含本機 SDK 路徑或個人環境資訊。
.env、私鑰、憑證、Token不得提交應由 CI secret store 或核准的金鑰系統提供。
*.backup-*、*.legacy-*驗收後刪除更新失敗時可復原；確認新平台與 release layout 通過後才移除。
Release Note、evidence、tag、URI／SHA-256保留這些是稽核紀錄，不是開發暫存。

推送前先做只讀檢查

git status --short --ignored
git diff --check
git ls-files
python3 -B scripts/pre_push_audit.py
python3 -B scripts/package_release.py --dry-run --allow-dirty

若舊 commit 已含敏感資料

  1. 先撤銷或輪替憑證；只刪目前檔案不能使舊 commit 安全。
  2. 確認受影響 repo、branch、tag、fork 與 CI log。
  3. 取得 repo 擁有者同意後，另案規劃 Git 歷史重寫與 force push；平台沒有自動執行這項破壞性操作。
  4. 通知協作者重新 clone 或依團隊程序修復本機分支。

公開維護 repo 的 commit 本來就是開發紀錄。若一般使用者應拿到不含歷史的版本，應發布經 verify_package.py 通過的 ZIP，不是讓使用者 clone 維護 repo。

8. 發行流程與阻擋條件

verify_release_readiness.py 採 fail-closed。必要檔不存在、hash 不符、URI 含 latest／current／snapshot／nightly、成品位於 release repo、簽章失敗、commit 不屬於 ref、工作樹不乾淨或 tag 不指向 HEAD，都會回傳失敗。

Release evidence 必要內容
  • schemaVersion: 2、產品與語意化版本（Semantic Versioning）。
  • 來源 repository、完整 commit SHA、允許的完整 ref。
  • 不可變 artifact URI、artifact SHA-256、signature URI／SHA-256／algorithm。
  • CI system、run ID，以及 build、test、lint、security、package。
  • SPDX 2.x 或 CycloneDX JSON SBOM。
  • SLSA provenance v1。
  • 獨立核准者與 publisher，兩者不可相同。

9. GitHub／GitLab 與隱私安全設定

本頁沒有 JavaScript、外部字型、CDN、分析工具、表單或網路請求；CSP（Content Security Policy）限制外部資源。內容使用通用 placeholder，不應填入內部 hostname、成品 URI、員工帳號或個人信箱。

推送前

  1. 確認 remote URL 沒有內嵌帳號密碼或 Token，使用 SSH 或不含憑證的 HTTPS URL。
  2. 公開 repo 的 Git user.email 建議使用 GitHub noreply 地址。
  3. 建立功能分支，不直接在 main 累積未審查變更。
  4. 執行自我檢查、測試、skill audit、pre-push audit 與 package dry-run。
  5. 檢查 staged diff 後再 commit 與 push。
git switch -c agent/publish-platform-guide
bash scripts/check.sh
python3 -B -m unittest discover -s tests -v
python3 -B scripts/audit_skills.py
python3 -B scripts/pre_push_audit.py
git add docs/index.html README.md
git diff --cached --check
git diff --cached --stat
git commit -m "docs: add platform architecture and onboarding guide"
git push -u origin agent/publish-platform-guide

Repository rules

  • Ruleset：要求 Pull Request、必要 checks，禁止 force push 與刪除 main。
  • Review：至少一位不是 PR 作者的協作者。CODEOWNERS 只有作者本人時，不得先啟用阻擋式 CODEOWNERS review。
  • Actions：預設使用 contents: read；需要寫入的 workflow 應個別說明。
  • Secret protection：啟用 secret scanning 與 push protection；敏感值放 GitHub Actions Secrets 或核准的 secret store。
  • Tags：為 v* 設定 tag ruleset，避免已發布 tag 被移動或刪除。

新增 collaborator／member

平台維護 repository 與 release repository 各自保存 scripts/manage_collaborators.py。預設只顯示計畫；加上 --apply 才會同步 GitHub／GitLab CODEOWNERS、加入成員並設定 PR／MR 與預設分支保護。

# 在兩個 repository 內分別執行
python3 -B scripts/manage_collaborators.py add <username>
python3 -B scripts/manage_collaborators.py add <username> --apply
python3 -B scripts/manage_collaborators.py check
  • GitHub 認證只讀取本機 gh auth login 狀態。
  • GitLab Token 只從 GITLAB_TOKEN 環境變數讀取，不寫入 CI 或 Git；必須是有效且包含 api scope 的 access token。
  • GitHub Free 的私人 repository 無法啟用 branch protection；腳本會在任何寫入前停止，不會改成公開或自動降低規則。
  • 遠端寫入先設定保護政策，再授予成員權限；GitHub 新帳號只先收到唯讀邀請，接受後重跑才升為 write。
  • GitLab 先確認 Maintainer／Owner 權限、active username、direct membership、group membership lock、分支與核准政策 API；強制 Code Owner 與 approval rule 需要 Premium／Ultimate，不支援時停止，不降低規則。
  • CI 只執行唯讀的 check，不持有 repository 管理 Token。

發佈本頁

  1. 將 GitHub Pages source 指向發布 branch 的 /docs 目錄，或使用組織既有 Pages workflow。
  2. 首頁使用 docs/index.html。
  3. 公開前搜尋真實本機路徑、email、內部 URI、Token、run ID 或未公開產品名稱。
  4. Pages 只展示說明；平台 ZIP 與產品成品仍留在 CI／成品平台。
